## 4.2 Arquitetura de execução (graph-loop)

### Topologia

```
                   ┌─────────────────────────────┐
                   │  OPUS 5 — orquestrador      │
                   │  · ordem de trabalho por item│
                   │  · revisão de diff           │
                   │  · decisão de gate           │
                   └──────────┬──────────────────┘
                              │ ordem de trabalho (1 item, escopo fechado)
                   ┌──────────▼──────────────────┐
     serial ───────│  SONNET 5 — executor        │────── fan-out (só onda 3)
     (ondas 0,1,   │  · edita · escreve teste     │       10 telas isoladas,
      2,4,5)       │  · roda gate local           │       sem colisão de arquivo
                   └──────────┬──────────────────┘
                              │ diff + saída de execução
                   ┌──────────▼──────────────────┐
                   │  LEDGER_EXECUCAO.md          │  ← estado persistido por item
                   └──────────────────────────────┘
```

**Por que quase tudo serial:** fan-out só compensa quando os ramos não colidem. Mapeei a colisão de arquivos (§4.6) e só a onda 3 tem paralelismo real — 10 telas, cada uma num arquivo próprio. Nas demais ondas, dois agentes editando `main.dart` ou `ci.yml` gastariam mais em resolução de conflito do que economizariam em relógio. Loop simples é a arquitetura certa aqui; swarm seria arquitetura de enfeite.

### Estado persistido — `LEDGER_EXECUCAO.md`

Uma linha por item, atualizada **antes** de passar ao próximo (mesmo padrão do `LEDGER_DE_AUDITORIA.md`, que funcionou):

```
| item | onda | status | commit | gate | evidência (saída literal) | iterações |
```

Sem isso o loop perde a memória entre sessões e refaz trabalho — foi o que produziu 86 arquivos sem commit em 31/07.

### Orçamento e critério de parada (por item)

| Limite | Valor | Ao esbarrar |
|---|---|---|
| Iterações de correção | 3 | Para, registra no ledger como **bloqueado**, devolve ao Opus para replanejar o item |
| Tamanho de diff | ~300 linhas (excl. testes e ledger) | Para e pede fatiamento do item |
| Escopo | só os arquivos listados na ordem de trabalho | Arquivo fora da lista = para e pergunta |
| Gate vermelho 2× seguidas pelo mesmo motivo | — | Para. Não tenta a terceira variação da mesma ideia |

**Regra de ouro do loop:** nenhum item é marcado verde sem saída de execução **colada literal** no ledger. Sem output, o item continua aberto — independentemente de quão certo o código pareça.

## 4.3 Protocolo de verificação — onde cada gate roda

Restrição dura, repetida da FASE 0: **não consigo rodar `flutter analyze` nem `flutter test`.** O sandbox tem 3,9 GB livres; o SDK 3.44.8 são 1,55 GB comprimidos + ~3,5 GB extraídos. Nenhum gate abaixo depende de eu executar Flutter.

| Gate | Onde roda | Quem confirma |
|---|---|---|
| `flutter analyze` | máquina do Lucas **e** CI (`ci.yml` já bloqueante) | saída colada / run verde |
| `flutter test --exclude-tags screenshots` | idem | idem |
| Goldens | CI, job `continue-on-error` | artefato `golden-failures` |
| `integration_test` | máquina do Lucas (precisa de device/Chrome) | saída colada |
| `curl -sI` de headers | CI (novo job) + manual | resposta HTTP |
| SCA (OSV) | **eu, no sandbox** — já rodou em 03/08 | executável por mim a qualquer momento |
| Contagens do repo (LOC, testes, commits, deps) | **eu, no sandbox** | executável por mim |
| Revisão de diff | Opus 5 | — |

**Consequência de planejamento:** empurrar o máximo de verificação para o CI, porque é o único lugar que executa Flutter **e** produz artefato durável. Verificação que só existe na sua máquina evapora quando você fecha o terminal.
